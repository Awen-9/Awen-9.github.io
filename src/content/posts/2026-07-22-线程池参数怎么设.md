线程池谁都会 `new`，但「核心线程数设多少」这个问题，十个后端八个答不利索。这篇把参数、估算方法、和几个经典坑一次讲清。

## 七个参数，先对号入座

```java
new ThreadPoolExecutor(
    4,                                    // corePoolSize  核心线程数
    16,                                   // maximumPoolSize 最大线程数
    60L, TimeUnit.SECONDS,                // keepAliveTime 空闲存活时间
    new LinkedBlockingQueue<>(1000),      // workQueue     任务队列
    Executors.defaultThreadFactory(),     // threadFactory 线程工厂
    new ThreadPoolExecutor.CallerRunsPolicy()   // handler  拒绝策略
);
```

执行顺序记牢：**核心线程 → 队列 → 非核心线程 → 拒绝策略**。注意是「队列满了才扩到最大线程数」，不是「核心满了就扩容」——这条顺序坑了无数人。

## 核心数怎么估：看任务类型

**CPU 密集型**（计算、序列化、加解密）：线程多了只会抢 CPU，上下文切换反而拖慢。

```
核心数 = CPU 核数 + 1
```

**IO 密集型**（查库、调 RPC、读写文件）：线程大部分时间在等，可以多开。

```
核心数 = CPU 核数 × (1 + 平均等待时间 / 平均计算时间)
```

经验值常取 `2 × CPU 核数` 起步。比如 8 核机器、任务 90% 时间在等 IO，可以给到十六到几十个。

```java
int cores = Runtime.getRuntime().availableProcessors();
ThreadPoolExecutor pool = new ThreadPoolExecutor(
        cores * 2, cores * 4, 60, TimeUnit.SECONDS, queue, factory, handler);
```

## 队列：最容易埋雷的地方

`Executors.newFixedThreadPool()` 用的 `LinkedBlockingQueue` **默认容量是 Integer.MAX\_VALUE**，等于一个不设上限的队列。后果是：任务堆积时永远进不了「扩容到最大线程数」那一步，队列越堆越长，最后 OOM。

```java
// ❌ 危险的默认值，队列长度理论无上限
Executors.newFixedThreadPool(8);

// ✅ 自己 new，队列给明确容量
new ThreadPoolExecutor(8, 32, 60, TimeUnit.SECONDS,
        new LinkedBlockingQueue<>(500), factory, new CallerRunsPolicy());
```

**阿里规约也是这么要求的：禁止用 `Executors` 创建线程池**，原因就是这几个默认队列/默认上限都是坑。

## 四种拒绝策略

策略

行为

适用

`AbortPolicy`（默认）

抛 `RejectedExecutionException`

需要感知失败的场景

`CallerRunsPolicy`

让提交任务的线程自己执行

想自动降速、不丢任务

`DiscardPolicy`

静默丢弃

允许丢的非关键任务

`DiscardOldestPolicy`

丢掉队列里最老的，再重试

只关心最新数据

生产上很多核心链路选 `CallerRunsPolicy`：队列满时让调用方亲自跑，自然形成背压，把压力顶回上游而不是无声地丢任务。

## 线程工厂：别忘给线程起名

线上排查问题，一 `jstack` 满屏 `pool-1-thread-37` 是灾难。自己写个工厂加上业务前缀：

```java
ThreadFactory factory = new ThreadFactoryBuilder()
        .setNameFormat("order-async-%d")
        .setUncaughtExceptionHandler((t, e) ->
                log.error("线程 {} 抛异常", t.getName(), e))
        .build();
```

（`ThreadFactoryBuilder` 来自 Guava；不引入的话手写一个 `AtomicInteger` 计数也几行。）

## 监控：参数不是设完就忘

线程池必须能被看见，否则出问题全靠猜。几个关键指标：

```java
ThreadPoolExecutor p = ...;
log.info("池大小={} 活跃={} 队列={} 已完成={}",
        p.getPoolSize(), p.getActiveCount(),
        p.getQueue().size(), p.getCompletedTaskCount());
```

-   `activeCount` 长期贴近 `maximumPoolSize` → 池太小
-   `queue.size()` 持续上涨 → 处理不过来，要么扩要么限流
-   `completedTaskCount` 增速骤降 → 某个任务卡住了

配合 Micrometer 把指标打进监控面板更好。

## 动态调参才是终局

参数写死在代码里，流量一波动就得改代码重新发版。理想的姿势是把 `corePoolSize` / `maximumPoolSize` 暴露到配置中心，运行时热更新：

```java
// ThreadPoolExecutor 自带 setter，配合配置中心监听即可
executor.setCorePoolSize(newCore);
executor.setMaximumPoolSize(newMax);
```

## 小结

-   顺序：核心 → 队列 → 最大 → 拒绝，别记反
-   核心数看任务类型：CPU 密集 `N+1`，IO 密集 `2N` 起
-   队列**一定要给容量**，别用 `Executors` 的默认无界队列
-   线程池不监控等于没设参数
