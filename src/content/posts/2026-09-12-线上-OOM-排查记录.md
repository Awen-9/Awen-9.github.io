凌晨两点被电话叫醒，订单服务每隔四十分钟重启一次。这篇把整个排查过程按时间线记下来——过程比结论重要，因为下次可能换个姿势翻车。

## 现象：不是崩溃，是「周期性重启」

看监控：堆曲线一条直线往上爬，爬到 4G 顶就断崖式下跌，然后循环。容器内存上限 4G，JVM 堆设的 `-Xmx3g`。这不是 leak 到死，是**有东西在持续堆积，GC 回收不掉**。

第一反应先保住现场，别急着重启。配置 JVM 在 OOM 时自己 dump：

```bash
java -XX:+HeapDumpOnOutOfMemoryError \
     -XX:HeapDumpPath=/data/dump/ \
     -Xms3g -Xmx3g -jar app.jar
```

如果服务已经在跑且没配这个参数，可以手动抓：

```bash
jmap -dump:live,format=b,file=/data/dump/heap.hprof <pid>
# 顺手看一眼各类占用
jmap -histo:live <pid> | head -30
```

`jmap` 会 STW 一下（`-dump:live` 触发一次 Full GC），线上低峰期操作，或者用 `jcmd <pid> GC.heap_dump`。

## 第二步：MAT 里找「谁在持有」

把 hprof 拖进 Eclipse MAT，直接看 **Dominator Tree**——它按「retained size」排序，也就是「干掉它之后能释放多少」：

```
Class Name                                | Shallow | Retained
com.example.order.LocalOrderCache         |  32 B   | 2.4 GB
  └─ java.util.concurrent.ConcurrentHashMap
       └─ java.util.HashMap$Node[]  (2,097,152 elements)
```

一眼看到根因：`LocalOrderCache` 里一个 `ConcurrentHashMap` 挂了 200 万个节点，retained size 2.4G。这个类名一看就知道是自己写的本地缓存。

## 第三步：回到代码

翻出代码，长这样：

```java
@Component
public class LocalOrderCache {
    private final Map<String, Order> cache = new ConcurrentHashMap<>();

    public Order get(String orderId) {
        Order o = cache.get(orderId);
        if (o == null) {
            o = loadFromDb(orderId);
            cache.put(orderId, o);   // ← 只进不出
        }
        return o;
    }
}
```

问题很直白：**只写不淘汰**。设计时的想法是「订单查一次就缓存，省一次 DB」，但没想过一个跑了两个月的服务会遇见多少个订单号。没有任何过期、没有任何容量上限，等于一个内存黑洞。

## 修复：换 Caffeine，给缓存划边界

本地缓存不是不能用，但必须有三样东西之一：容量上限、过期时间、或弱/软引用。直接换成 Caffeine：

```java
@Bean
public Cache<String, Order> orderCache() {
    return Caffeine.newBuilder()
            .maximumSize(50_000)              // 硬上限，超了按 W-TinyLFU 淘汰
            .expireAfterWrite(Duration.ofMinutes(10))
            .recordStats()                    // 开命中率统计，方便回头调
            .build();
}
```

```java
public Order get(String orderId) {
    return cache.get(orderId, this::loadFromDb);
}
```

改完观察一天：堆曲线在 1.5G 上下平稳波动，命中率 92%，GC 次数从每小时 40 多次掉到个位数。

## 复盘：几条写进团队规范的经验

1.  **本地缓存必须有边界**。没上限的 `Map` 缓存一律按 bug 处理，评审直接打回。
2.  **JVM 一定要配 `HeapDumpOnOutOfMemoryError`**。这次能这么快定位，全靠现场还在。
3.  **`jstat -gcutil <pid> 1000` 看趋势**，比看单次快照有用：

```bash
jstat -gcutil 1 1000 10
#   S0   S1    E     O     M   CCS   YGC  YGCT   FGC  FGCT
#  0.00 62.5  88.4  99.1 94.2 91.1  1203 18.4    88  62.7   ← O 区几乎满，FGC 频繁
```

4.  **不要迷信「加了缓存就快」**。缓存是把双刃剑：加速读，同时把「数据什么时候过期」的责任揽到了自己身上。

事后想想，如果当初 `LocalOrderCache` 里加一行 `CacheBuilder`，这场半夜的电话根本不会发生。教训不便宜，但记下了。
