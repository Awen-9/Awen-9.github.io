「缓存三兄弟」——穿透、击穿、雪崩，名字唬人，但很多人答得含糊。它们的区别说到底是「谁失效了」：穿透是**查不存在的数据**，击穿是**某个热点 key 失效**，雪崩是**大批 key 同时失效**。分清了，解法自然就出来了。

## 一、穿透：查一个永远不存在的数据

**场景**：恶意请求拿着 `userId = -1` 疯狂刷接口。缓存里没有，每次都打到 DB，DB 里也没有，于是缓存永远建不起来，每次请求都穿透到数据库。

**解法一：缓存空值**。查不到也写进缓存，值给个特殊标记，设短一点的过期时间。

```java
public User getUser(Long id) {
    String key = "user:" + id;
    String cached = redis.get(key);
    if (cached != null) {
        return "NULL".equals(cached) ? null : JSON.parse(cached, User.class);
    }
    User user = userMapper.selectById(id);
    if (user == null) {
        redis.setex(key, 60, "NULL");     // 空值也缓存，防重复穿透
        return null;
    }
    redis.setex(key, 3600, JSON.toJSONString(user));
    return user;
}
```

缺点也很明显：如果是海量不同的非法 id，缓存里会被塞满垃圾 key。这时候用解法二。

**解法二：布隆过滤器**，在缓存前面挡一道。把所有合法的 id 预先灌进布隆过滤器，请求先问它「这个 id 可能存在吗」：

```java
if (!bloomFilter.mightContain(id)) {
    return null;                          // 一定不存在，直接返回
}
// 可能存在（有小概率误判），继续走缓存 + DB
```

布隆过滤器**说「不存在」就一定不存在，说「存在」可能误判**，但绝不会漏掉真实数据，正好适合挡穿透。

## 二、击穿：热点 key 突然过期

**场景**：某个秒杀商品的缓存刚好到期，这一刻成千上万的请求同时发现缓存没了，齐刷刷去查 DB 重建缓存——DB 瞬间被打爆。

**解法一：互斥锁**，保证只有一个线程去重建。

```java
String cached = redis.get(key);
if (cached != null) return cached;

String lockKey = "lock:" + key;
// setIfAbsent = SETNX，只有拿到锁的线程能去查 DB
if (redis.setIfAbsent(lockKey, "1", Duration.ofSeconds(10))) {
    try {
        User user = loadFromDb(key);      // 双检，拿锁后缓存可能已被别人建好
        redis.setex(key, 3600, JSON.toJSONString(user));
        return user;
    } finally {
        redis.delete(lockKey);
    }
} else {
    Thread.sleep(50);                     // 没抢到锁，稍等再读缓存
    return getUser(key);
}
```

**解法二：逻辑过期**。缓存永不「物理过期」，而是在 value 里塞一个逻辑过期时间，读到已过期的数据时**直接返回旧值**，另起一个异步线程去更新。牺牲一点一致性，换来零阻塞。适合能容忍短暂脏读的场景。

**解法三：热点数据永不过期**，靠后台定时任务或消息队列主动刷新。

## 三、雪崩：大批 key 同时失效

**场景一**：系统启动时批量预热缓存，统一设了 `expire 3600`，一小时后集体过期，DB 迎来洪峰。  
**场景二**：Redis 节点整个挂掉，所有请求直接打到 DB。

**解法一：过期时间加随机抖动**，把「同时」打散：

```java
// 基础 1 小时，再随机加 0~5 分钟
long ttl = 3600 + ThreadLocalRandom.current().nextInt(300);
redis.setex(key, ttl, value);
```

**解法二：多级缓存**。本地 Caffeine + Redis 两层，Redis 挂了本地还能顶一阵。

**解法三：高可用兜底**。Redis 用哨兵/集群，避免单点；DB 前面加限流和熔断（Sentinel），真被打到时至少能快速失败而不是拖垮整个库。

## 最后一句

缓存策略没有银弹。**先想清楚业务能容忍多大的不一致**——强一致就别用缓存，能容忍秒级延迟就上逻辑过期，能容忍分钟级就老老实实 `setex`。方案是结果，一致性要求才是出发点。
