「我明明加索引了，怎么还全表扫描？」——这个问题几乎每个月都要被问一次。索引失效不是玄学，把 `EXPLAIN` 学会看，基本都能定位。这篇按场景列，配执行计划。

## 先建张表

```sql
CREATE TABLE `t_order` (
  `id`         BIGINT       NOT NULL AUTO_INCREMENT,
  `order_no`   VARCHAR(32)  NOT NULL COMMENT '订单号',
  `user_id`    BIGINT       NOT NULL,
  `status`     TINYINT      NOT NULL COMMENT '1待付款 2已付款 3已取消',
  `amount`     DECIMAL(10,2) NOT NULL,
  `created_at` DATETIME     NOT NULL,
  PRIMARY KEY (`id`),
  KEY `idx_user_status_created` (`user_id`, `status`, `created_at`)
) ENGINE=InnoDB;
```

联合索引 `(user_id, status, created_at)`，下面所有例子都在它上面翻车。

## EXPLAIN 里只要看三个字段

字段

关注点

`type`

访问类型，`ref`/`range` 可用，`ALL` = 全表扫，`index` = 扫全索引

`key`

实际用了哪个索引，`NULL` = 没用上

`Extra`

`Using where` / `Using filesort` / `Using index`（覆盖索引）

## 场景一：最左前缀被跳过

```sql
-- ✅ 用得上：(user_id)
SELECT * FROM t_order WHERE user_id = 100;

-- ❌ 用不上：跳过了最左列 user_id
SELECT * FROM t_order WHERE status = 2;

-- ✅ 用得上：虽然跳了中间列，但 user_id 在
SELECT * FROM t_order WHERE user_id = 100 AND created_at > '2026-01-01';
```

规则：联合索引从左往右匹配，**中间断了，后面的列就都失效**。

## 场景二：在索引列上做运算 / 用函数

```sql
-- ❌ 索引列被函数包住
SELECT * FROM t_order WHERE DATE(created_at) = '2026-08-01';

-- ✅ 改成范围
SELECT * FROM t_order
WHERE created_at >= '2026-08-01 00:00:00'
  AND created_at <  '2026-08-02 00:00:00';
```

## 场景三：隐式类型转换（最隐蔽）

`order_no` 是 `VARCHAR`，却用数字去查：

```sql
-- ❌ 字符串列和数字比较，MySQL 把列转成数字，索引直接失效
SELECT * FROM t_order WHERE order_no = 20260828001;

-- ✅ 加引号
SELECT * FROM t_order WHERE order_no = '20260828001';
```

反过来，如果列是数字、传字符串，通常还是能走索引的——**哪个方向转换决定了是否失效**，这点容易记反。

## 场景四：前导模糊

```sql
SELECT * FROM t_order WHERE order_no LIKE '202608%';   -- ✅ 走 range
SELECT * FROM t_order WHERE order_no LIKE '%0828%';    -- ❌ 全表扫
```

## 场景五：OR 两侧有一侧没索引

```sql
-- user_id 有索引，remark 没有 → 整体退化成全表扫
SELECT * FROM t_order WHERE user_id = 100 OR remark = 'xxx';
```

要么给 `remark` 也补索引，要么用 `UNION ALL` 拆开。

## 场景六：范围查询之后的列失效

```sql
-- created_at 是范围，它后面的列没法再用于定位（但可用于覆盖）
SELECT * FROM t_order
WHERE user_id = 100 AND status = 2 AND created_at > '2026-01-01';
-- key = idx_user_status_created，range 只吃前两列的等值 + 第三列的范围
```

所以设计联合索引时，**等值列放前面、范围列放最后**。

## 场景七：不等于 / NOT IN / IS NOT NULL

`!=`、`<>`、`NOT IN` 大部分情况会让优化器放弃索引；`IS NULL` 能走索引、`IS NOT NULL` 通常不能。不是绝对，取决于数据分布和优化器判断的代价。

## 场景八：优化器算了一笔账，主动放弃

即使写法完美，优化器也可能觉得「走索引回表 + 随机 IO 还不如直接全表扫」。当命中行数占比很高（大概超过 20%~30%）时就会这样。用 `EXPLAIN` 确认，必要时 `FORCE INDEX` 或改写。

## 一个万能的小抄

```sql
EXPLAIN SELECT ...;
-- 找到慢 SQL 后别忘看真实的执行代价
EXPLAIN ANALYZE SELECT ...;   -- MySQL 8.0.18+，会真跑一遍给实际耗时
```

配合慢查询日志：

```sql
SET GLOBAL slow_query_log = ON;
SET GLOBAL long_query_time = 1;
SET GLOBAL log_queries_not_using_indexes = ON;
```

## 小结

索引失效的根子就一句话：**只要让优化器没法用「有序」这个优势，索引就白建了**——函数、运算、隐式转换、前导模糊、OR，本质上都在破坏有序性。写 SQL 时多想一步「这个条件能不能用上 B+ 树的有序区间」，八成问题当场就避免了。
