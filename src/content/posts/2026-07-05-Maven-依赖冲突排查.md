编译期一切正常，一跑就 `NoSuchMethodError` 或 `ClassNotFoundException`——八成是依赖冲突。这篇把 Maven 的仲裁规则讲清楚，再给一套排查手法。

## Maven 怎么决定用哪个版本

两个 jar 都间接引了同一个库、版本还不一样，Maven 按两条规则裁决：

1.  **最短路径优先**：依赖树里离当前项目层级更浅的赢
2.  **最先声明优先**：路径一样长时，`pom.xml` 里先声明的赢

```
A → B → C 1.0        (路径长度 3)
A → D → E → C 2.0    (路径长度 4)
```

这里 C 用 **1.0**，因为到 1.0 的路径更短。要强制改用 2.0，就得显式干预。

## 第一招：dependency:tree 看全貌

```bash
mvn dependency:tree
# 只看某个坐标
mvn dependency:tree -Dincludes=org.slf4j:slf4j-api
# 输出到文件，冲突多的时候好用
mvn dependency:tree -Dverbose > tree.txt
```

`-Dverbose` 会把「被省略的依赖」（omitted for conflict / duplicate）也打出来，冲突一眼可见：

```
+- com.example:a:jar:1.0
|  \- org.slf4j:slf4j-api:jar:1.7.20:compile
\- com.example:b:jar:1.0
   \- (org.slf4j:slf4j-api:jar:1.7.36:compile - omitted for conflict with 1.7.20)
```

## 第二招：定位到底是哪个类在打架

报错长这样：

```
java.lang.NoSuchMethodError:
  com.google.common.collect.ImmutableList.of(Ljava/lang/Object;...)Ljava/util/List;
```

拿类名和 jar 包名去 `dependency:tree -Dincludes=` 里查，通常一查一个准。

```bash
mvn dependency:tree -Dincludes=com.google.guava:guava
```

## 三招解法

### 1\. exclusions：把那根不想要的树枝剪掉

```xml
<dependency>
    <groupId>com.example</groupId>
    <artifactId>legacy-sdk</artifactId>
    <version>1.0</version>
    <exclusions>
        <exclusion>
            <groupId>com.google.guava</groupId>
            <artifactId>guava</artifactId>
        </exclusion>
    </exclusions>
</dependency>
```

### 2\. dependencyManagement：统一版本闸门（推荐）

在父 pom 里把版本钉死，子模块只写 groupId + artifactId：

```xml
<dependencyManagement>
    <dependencies>
        <dependency>
            <groupId>com.google.guava</groupId>
            <artifactId>guava</artifactId>
            <version>33.2.1-jre</version>
        </dependency>
    </dependencies>
</dependencyManagement>
```

### 3\. 直接声明（最后手段）

```xml
<dependency>
    <groupId>com.google.guava</groupId>
    <artifactId>guava</artifactId>
    <version>33.2.1-jre</version>
</dependency>
```

显式声明的路径最短，一定赢。但这只是「压」住了问题，别的模块可能还在引老版本，治标不治本——优先用 `dependencyManagement`。

## 用 enforcer 提前拦下来

与其运行时报错，不如构建时就失败：

```xml
<plugin>
    <groupId>org.apache.maven.plugins</groupId>
    <artifactId>maven-enforcer-plugin</artifactId>
    <executions>
        <execution>
            <id>ban-duplicate-classes</id>
            <goals><goal>enforce</goal></goals>
            <configuration>
                <rules>
                    <dependencyConvergence/>   <!-- 同一坐标出现多个版本就报错 -->
                </rules>
            </configuration>
        </execution>
    </executions>
</plugin>
```

`dependencyConvergence` 会在检测到「同一 groupId:artifactId 有多个版本」时直接让构建失败，把冲突扼杀在提交前。

## 常见冲突源，先记住这几个

库

冲突表现

`slf4j-api` / `logback`

日志不输出、`NoSuchMethodError`

`guava`

`ImmutableList` / `Stopwatch` 方法找不到

`jackson-*`

序列化行为不一致，`ClassNotFound`

`netty`

`NoSuchMethodError`，常见于各种 RPC 框架

`spring-*`

版本错配导致启动失败

## 小结

排查流程固定三步：`dependency:tree -Dverbose` 找冲突 → `-Dincludes=` 精确定位 → `dependencyManagement` 统一版本，最后用 `enforcer` 上把锁。下次再见到 `NoSuchMethodError`，别再一顿乱加 `exclusions` 了。
