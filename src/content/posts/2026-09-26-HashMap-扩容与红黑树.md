HashMap 大概是面试被问得最多的集合类。背答案容易，但把 `put()` 一路读到 `resize()`，才会发现里面几个数字都不是随便定的。

## put 的三步走

1.8 的 `putVal()` 逻辑可以压成三步：

1.  算下标：`(n - 1) & hash`
2.  该位置空 → 直接放
3.  该位置有东西 → 是链表就尾部插入并判断要不要树化，是红黑树就走树的插入

```java
final V putVal(int hash, K key, V value, boolean onlyIfAbsent, boolean evict) {
    Node<K,V>[] tab; Node<K,V> p; int n, i;
    if ((tab = table) == null || (n = tab.length) == 0)
        n = (tab = resize()).length;
    if ((p = tab[i = (n - 1) & hash]) == null)
        tab[i] = newNode(hash, key, value, null);
    // ... 命中已有桶，走链表 / 红黑树
}
```

## 为什么下标是 (n - 1) & hash

数组长度 n 永远是 2 的幂，所以 `n - 1` 的二进制是「低位全 1」。`&` 一下相当于对低位取模，但比 `%` 快得多。这也是为什么**容量必须是 2 的幂**——不满足的话低位会有 0，某些下标永远取不到，桶分布直接塌掉。

还有个前提：`hash` 得先被「扰动」过。

```java
static final int hash(Object key) {
    int h;
    return (key == null) ? 0 : (h = key.hashCode()) ^ (h >>> 16);
}
```

把高 16 位异或到低 16 位，是因为下标只看低位——如果不扰动，一批 hashCode 只有高位不同的 key 会全部撞进同一个桶。

## 负载因子 0.75 的取舍

```java
static final float DEFAULT_LOAD_FACTOR = 0.75f;
```

-   太小：桶还没装满就扩，浪费空间，扩容还很频繁
-   太大：冲突变多，链表变长，查询退化

0.75 是空间和时间的经验折中：按泊松分布，长度到 8 的概率已经低到千万分之六左右。

## 树化阈值为什么是 8 和 6

```java
static final int TREEIFY_THRESHOLD = 8;    // 链表长度 ≥ 8 转红黑树
static final int UNTREEIFY_THRESHOLD = 6;  // 红黑树节点 ≤ 6 退回链表
```

阈值不设成同一个数（8 转树、6 退链），是为了**留一条缓冲带**，避免在 7、8 之间反复横跳，白白消耗转换成本。另外树化还有个前置条件：数组长度至少 64，否则优先扩容而不是转树。

## 扩容：1.8 省掉 rehash 的那个技巧

扩容会把容量翻倍，然后重新分配所有元素。1.7 是每个元素重新算一遍 hash 定位；1.8 发现一个规律：容量翻倍后，元素要么留在原下标 `j`，要么移动到 `j + oldCap`——只看 hash 里新增的那一位是 0 还是 1。

```java
if ((e.hash & oldCap) == 0) {
    // 留在低位链 loHead
} else {
    // 去高位链 hiHead，位置是 j + oldCap
}
```

`oldCap` 是 2 的幂，`&` 出来只有两种结果，于是整条链被拆成两条，直接挂到新表的两个位置上，**既不用重新算 hash，也避免了 1.7 头插法导致的链表成环问题**。

## 几个容易踩的点

-   **初始容量别瞎写**：预估 1000 个元素却 `new HashMap<>(1000)`，其实会扩到 2048。老实传业务量，让它自己算。
-   **key 必须不可变**：用可变对象当 key 且改了字段，hash 变了就再也找不回来。
-   **并发场景直接上 ConcurrentHashMap**：1.8 的 HashMap 扩容时多线程并发可能丢数据、也可能读到环，不要赌。
