《深入理解 Java 虚拟机》读书笔记：内存与 GC

2026 年 05 月 29 日 读书笔记 1.1k 字 约 3 分钟 0 次阅读

本文目录

《深入理解 Java 虚拟机》翻过两遍，第一遍是面试前突击，第二遍是线上出问题后带着疑问回炉。笔记按「能随时回查」的思路整理，不追求全覆盖。

运行时数据区

区域 线程私有？ 作用 会不会 OOM
程序计数器 私有 当前字节码行号 唯一不会 OOM 的
虚拟机栈 私有 方法栈帧（局部变量表等） StackOverflowError / OOM
本地方法栈 私有 native 方法 同上
堆 共享 对象实例 最常见的 OOM 来源
方法区 / 元空间 共享 类信息、常量、静态变量 1.8 后移出堆，用本地内存
运行时常量池 共享 字面量、符号引用 intern() 滥用会撑爆

一个常被忽视的点：方法区在 1.8 从永久代换成了元空间，用的本地内存，所以 -XX:MaxPermSize 那套参数在新版本已经无效了，取而代之是 -XX:MaxMetaspaceSize。

对象是怎么创建出来的

  1. 类加载检查：常量池里能不能找到这个类的符号引用
  2. 分配内存：指针碰撞（内存规整）或空闲列表（内存不规整）
  3. 内存置零：保证实例字段有默认值
  4. 设置对象头：Mark Word、类型指针
  5. 执行 <init>：构造函数

分配时还有个 TLAB（本地线程分配缓冲）：每个线程先在堆里划一小块私有区域，避免每次分配都要同步。这就是为什么多线程下 new 依旧很快。

对象在内存里分三块：对象头 + 实例数据 + 对齐填充。对象头里存着 Mark Word（哈希、GC 分代年龄、锁状态）和类型指针。

怎么判断对象该死

  • 引用计数：简单，但解决不了循环引用，JVM 没用它
  • 可达性分析（JVM 用的）：从一组「GC Roots」出发，走不到的对象即可回收

GC Roots 包括：虚拟机栈里引用的对象、方法区静态属性引用的、常量引用的、本地方法栈 JNI 引用的。

三次「自赎」的机会

一个对象被判「不可达」也不会立刻死，最多经历两次标记 + 一次 finalize()。所以别指望靠 finalize() 兜底释放资源，早就被标记为 deprecated 了，用 try-with-resources 或 Cleaner。

GC 算法

算法 思路 缺点 用在哪
标记-清除 标记可回收，直接清 碎片多 老年代（CMS）
复制 分两块，存活对象搬到另一半 浪费一半空间 新生代
标记-整理 标记后把存活对象往一端挪 移动成本高 老年代

为什么新生代用复制、老年代用整理？因为新生代**「朝生夕死」**，存活率极低，复制成本小；老年代存活率高，复制不划算。

分代与收集器

堆默认按 1 : 2 分新生代 / 老年代，新生代内部又分 Eden : S0 : S1 = 8 : 1 : 1。对象经历一次 Minor GC 年龄 +1，到 15 岁（默认）晋升老年代。

常见收集器：

  • Serial：单线程，适合小内存客户端
  • ParNew / Parallel Scavenge：多线程，关注吞吐
  • CMS：低停顿，标记-清除，有碎片、有 Concurrent Mode Failure 风险
  • G1（现在的主流）：把堆切成 Region，可预测停顿，整体是标记-整理
  • ZGC / Shenandoah：超低停顿（亚毫秒级），大堆场景

一条命令搞定大部分 GC 参数

-Xlog:gc* 是 JDK 9+ 的统一日志格式，替代了老掉牙的一堆 -XX:+PrintGCDetails。

一点体会

这本书最值钱的不是「背参数」，而是理解**「JVM 为什么这么设计」**——分代是为了把「大部分对象很快死掉」这个统计规律转化成性能。想明白动机，参数自然就记住了；只背参数，出问题还是抓瞎。
