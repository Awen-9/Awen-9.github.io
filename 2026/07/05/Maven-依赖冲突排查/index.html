Maven 依赖冲突的定位与解决

本文目录

编译期一切正常，一跑就 NoSuchMethodError 或 ClassNotFoundException——八成是依赖冲突。这篇把 Maven 的仲裁规则讲清楚，再给一套排查手法。

Maven 怎么决定用哪个版本

两个 jar 都间接引了同一个库、版本还不一样，Maven 按两条规则裁决：

  1. 最短路径优先：依赖树里离当前项目层级更浅的赢
  2. 最先声明优先：路径一样长时，pom.xml 里先声明的赢

这里 C 用 1.0，因为到 1.0 的路径更短。要强制改用 2.0，就得显式干预。

三招解法

1. exclusions：把那根不想要的树枝剪掉

2. dependencyManagement：统一版本闸门（推荐）

3. 直接声明（最后手段）

显式声明的路径最短，一定赢。但这只是「压」住了问题，别的模块可能还在引老版本，治标不治本——优先用 dependencyManagement。

dependencyConvergence 会在检测到「同一 groupId:artifactId 有多个版本」时直接让构建失败，把冲突扼杀在提交前。

常见冲突源，先记住这几个

库 冲突表现
slf4j-api / logback 日志不输出、NoSuchMethodError
guava ImmutableList / Stopwatch 方法找不到
jackson-* 序列化行为不一致，ClassNotFound
netty NoSuchMethodError，常见于各种 RPC 框架
spring-* 版本错配导致启动失败

小结

排查流程固定三步：dependency:tree -Dverbose 找冲突 → -Dincludes= 精确定位 → dependencyManagement 统一版本，最后用 enforcer 上把锁。下次再见到 NoSuchMethodError，别再一顿乱加 exclusions 了。
