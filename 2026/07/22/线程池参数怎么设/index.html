线程池参数到底该怎么设：从 IO 密集说起

本文目录

线程池谁都会 new，但「核心线程数设多少」这个问题，十个后端八个答不利索。这篇把参数、估算方法、和几个经典坑一次讲清。

七个参数，先对号入座

执行顺序记牢：核心线程 → 队列 → 非核心线程 → 拒绝策略。注意是「队列满了才扩到最大线程数」，不是「核心满了就扩容」——这条顺序坑了无数人。

核心数怎么估：看任务类型

CPU 密集型（计算、序列化、加解密）：线程多了只会抢 CPU，上下文切换反而拖慢。

IO 密集型（查库、调 RPC、读写文件）：线程大部分时间在等，可以多开。

经验值常取 2 × CPU 核数 起步。比如 8 核机器、任务 90% 时间在等 IO，可以给到十六到几十个。

队列：最容易埋雷的地方

Executors.newFixedThreadPool() 用的 LinkedBlockingQueue 默认容量是 Integer.MAX_VALUE，等于一个不设上限的队列。后果是：任务堆积时永远进不了「扩容到最大线程数」那一步，队列越堆越长，最后 OOM。

阿里规约也是这么要求的：禁止用 Executors 创建线程池，原因就是这几个默认队列/默认上限都是坑。

四种拒绝策略

策略 行为 适用
AbortPolicy（默认） 抛 RejectedExecutionException 需要感知失败的场景
CallerRunsPolicy 让提交任务的线程自己执行 想自动降速、不丢任务
DiscardPolicy 静默丢弃 允许丢的非关键任务
DiscardOldestPolicy 丢掉队列里最老的，再重试 只关心最新数据

生产上很多核心链路选 CallerRunsPolicy：队列满时让调用方亲自跑，自然形成背压，把压力顶回上游而不是无声地丢任务。

监控：参数不是设完就忘

线程池必须能被看见，否则出问题全靠猜。几个关键指标：

  • activeCount 长期贴近 maximumPoolSize → 池太小
  • queue.size() 持续上涨 → 处理不过来，要么扩要么限流
  • completedTaskCount 增速骤降 → 某个任务卡住了

配合 Micrometer 把指标打进监控面板更好。

小结

  • 顺序：核心 → 队列 → 最大 → 拒绝，别记反
  • 核心数看任务类型：CPU 密集 N+1，IO 密集 2N 起
  • 队列一定要给容量，别用 Executors 的默认无界队列
  • 线程池不监控等于没设参数
